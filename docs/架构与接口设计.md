## 1. 总体架构

### 1.1 分层与数据流

```
                         ┌──────────────────────────────────────────────┐
                         │                 cli (AppSupport)              │
                         │   dispatchSubcommand: Default | Run | Diagnose │
                         └───────┬───────────────┬──────────────────────┘
                   run 子命令    │               │   diagnose 子命令
                                 ▼               │
                 ┌──────────────────────────┐   │   读盘 .trace.json
                 │  semantic_trace           │   │
                 │   event_emitter            │   │
                 │     scanSourceToTrace()    │   │
                 │     constructSampleTrace() │   │
                 │   serde (exportToFile)     │   │
                 └────────────┬───────────────┘   │
                              │ 写盘 .trace.json  │
                              ▼                   ▼
                   ┌──────────────────────────────────────────────┐
                   │            diagnostic_scheduler                │
                   │  run():  emitter→serde(导出)                    │
                   │  diagnose(): serde(加载)→pattern_matcher→渲染   │
                   └────────────┬───────────────────┬──────────────┘
                                │                   │
              ┌─────────────────▼──┐      ┌─────────▼────────────────┐
              │ local_diagnostic_  │      │ 复用 diagnostic_core     │
              │ lib                │      │ (compiler_diagnostic.    │
              │  pattern_matcher   │      │  diagnostics)            │
              │  formal_library    │      │ DiagnosticMessage /      │
              │  repair_resource   │      │ Span / FixSuggestion …   │
              └────────────────────┘      └──────────────────────────┘

  在线/离线两条输入路径，在 diagnostic_scheduler 统一收敛为同一诊断逻辑。
  确定性要求：相同 Trace → 相同输出；无 AI / 网络 / 随机 / 时间依赖。
```

## 3. 关键类型与接口（仓颉签名草图，可直接指导编码）

### 3.1 Trace Schema（`semantic_trace.trace_schema`）

字段严格对齐需求 F-P0-1；位置/范围复用 `diagnostics.SourceLoc`/`Span`，**不另起一套**。

```cangjie
package compiler_diagnostic.semantic_trace

import compiler_diagnostic.diagnostics.SourceLoc
import compiler_diagnostic.diagnostics.Span

// ===== 版本常量（加载时校验 MAJOR） =====
public let TRACE_SCHEMA_VERSION: String = "1.0.0"
public let TRACE_SCHEMA_MAJOR: Int64 = 1

// ===== 机器执行层 =====
public struct StackFrame {
    public var function: String
    public var loc: SourceLoc
    public init(function!: String, loc!: SourceLoc) {
        this.function = function
        this.loc = loc
    }
}

public struct SymbolValue {
    public var name: String
    public var type: String
    public var valueRepr: String
    public init(name!: String, type!: String, valueRepr!: String) {
        this.name = name
        this.type = type
        this.valueRepr = valueRepr
    }
}

public struct ExceptionInfo {
    public var type: String
    public var message: String
    public init(type!: String, message!: String) {
        this.type = type
        this.message = message
    }
}

public struct MachineEvent {
    public var stepId: Int64
    public var kind: String           // "step"|"call"|"return"|"branch"|"array-access"|"var-bind"|"exception"|…
    public var loc: SourceLoc
    public var stack: Array<StackFrame>
    public var symbols: Array<SymbolValue>
    public var path: String          // "then"|"else"|循环迭代号…，供模式匹配做路径特征
    public var exception: Option<ExceptionInfo>
    public init(stepId!: Int64, kind!: String, loc!: SourceLoc,
                stack!: Array<StackFrame>, symbols!: Array<SymbolValue>,
                path!: String, exception!: Option<ExceptionInfo>) { /* … */ }
}

// ===== 仓颉语义事件层（P2 预留结构；本迭代可空数组，OQ3 确认接受） =====
public struct SemanticEvent {
    public var stepId: Int64
    public var kind: String           // "conditional-eval"|"loop-enter"|"loop-iter"|"call-return"|"symbol-bind"|"type-infer"|"ownership-transfer"|"match-arm"|"module-import"
    public var loc: SourceLoc
    public var detail: Map<String, String>   // 结构化信息（类型/值/分支等），确定性 key-value
    public var relatedSpan: Option<Span>
    public init(stepId!: Int64, kind!: String, loc!: SourceLoc,
                detail!: Map<String, String>, relatedSpan!: Option<Span>) { /* … */ }
}

// ===== 根结构元信息 =====
public struct GeneratorInfo {
    public var tool: String
    public var version: String
    public var sdk: String
    public init(tool!: String, version!: String, sdk!: String) { /* … */ }
}

public struct ProgramInfo {
    public var entry: String
    public var args: Array<String>
    public init(entry!: String, args!: Array<String>) { /* … */ }
}

public struct Trace {
    public var schemaVersion: String
    public var generator: GeneratorInfo
    public var program: ProgramInfo
    public var machineEvents: Array<MachineEvent>
    public var semanticEvents: Array<SemanticEvent>
    public init(schemaVersion!: String, generator!: GeneratorInfo, program!: ProgramInfo,
                machineEvents!: Array<MachineEvent>, semanticEvents!: Array<SemanticEvent>) { /* … */ }
}
```

**版本兼容策略**：
- 仅校验 **MAJOR**。加载时解析 `schemaVersion` 的 `MAJOR`；若 `loadedMajor != TRACE_SCHEMA_MAJOR`（即 `!= 1`）→ 拒绝（返回 `Err`，不静默损坏）。
- MINOR/PATCH 不兼容不阻断（向后兼容新增字段：解析时遇到未知字段忽略；序列化时始终写出当前全部字段）。

### 3.2 event_emitter（`semantic_trace.event_emitter`）—— 本迭代如何「产生 Trace」

**OQ1 明确决策**：P0/P1 **不做真实运行时插桩**（属 P2）。本迭代 `run` 的 Trace 来源采用「务实静态合成」：

1. `scanSourceToTrace(file)`：读取 `.cj` 源文件文本，做**轻量关键字/结构启发式扫描**，合成机器层 `MachineEvent` 序列（如识别 `arr[idx]` → `array-access` 事件并附 `exception`；识别 `match` 无 `_` 臂 → `branch`/`exception` 事件；识别 `move(x)` 后 `x` 再使用 → `var-bind`/`exception` 事件）。
2. `constructSampleTrace(kind)`：受控样例构造，供 `samples/` 下已知文件与单元测试直接映射事件序列（确定性最强）。
3. `buildFromEvents(events, entry, args)`：程序化构造入口（测试与 P2 真实捕获共用）。

```cangjie
package compiler_diagnostic.semantic_trace

import std.fs.*
import compiler_diagnostic.diagnostics.SourceLoc

public class EventEmitter {
    /// 程序化构造（测试 / 未来运行时捕获共用入口）
    public static func buildFromEvents(
        events: Array<MachineEvent>,
        entry!: String,
        args!: Array<String> = Array<String>()
    ): Trace { /* 组装 Trace，generator 填 "semantic_trace/event_emitter" + SDK 版本 */ }

    /// 受控样例构造（samples/ 与 UT 用），kind ∈ {"array-oob","type-mismatch","use-after-move","non-exhaustive-match"}
    public static func constructSampleTrace(kind: String): Trace { /* 返回该故障对应的事件序列 */ }

    /// ⚠️ P0 在线路径务实实现：轻量静态扫描源码 -> machine-layer Trace
    /// 真实运行时插桩（AST/IR 埋点）属 P2，此处仅关键字/结构启发式合成，非字节级执行轨迹。
    public static func scanSourceToTrace(sourceFile: String): Trace {
        // 1) 读文件文本（std.fs）；2) 逐行正则/子串启发式识别故障签名；
        // 3) 为每个命中点 emit 一个 MachineEvent（带 loc/path/exception）；
        // 4) buildFromEvents(...) 收口。文件读取失败返回空 machineEvents 的 Trace（diagnose 端走未命中回退）。
    }
}
```

> 标记：静态扫描只是 P2 完整埋点的**占位**；架构不依赖任何尚不存在的 JVM/VM 插桩能力。扫描的「识别规则」与种子故障模式一一对应，便于 P2 升级为真实捕获后无缝替换 `event_emitter` 内部实现。

### 3.5 故障模式库数据模型（`local_diagnostic_lib.formal_library`）

匹配规则用「事件条件 + 有序序列」表达，**可序列化、可人工编辑**（满足需求 F-P1-1；AI/ML/网络/随机一律禁止）。

```cangjie
package compiler_diagnostic.local_diagnostic_lib

import compiler_diagnostic.diagnostics.Severity
import compiler_diagnostic.diagnostics.ErrorCategory
import compiler_diagnostic.diagnostics.FixSuggestion
import compiler_diagnostic.diagnostics.RelatedInfo
import compiler_diagnostic.diagnostics.Span

/// 单条事件匹配条件（可序列化、可人工编辑）
public struct EventCondition {
    public var kind: Option<String>        // 事件 kind 等于
    public var exceptionType: Option<String> // exception.type 等于（种子主要用此字段）
    public var hasException: Bool          // 是否要求存在 exception
    public var path: Option<String>        // path 等于
    public var symbolName: Option<String>  // symbols 中含此 name
    public var symbolType: Option<String>  // 该 symbol 的 type 等于
    public var negate: Bool = false        // 条件取反（表达「未出现某事件」）
}

/// 匹配规约：朴素序列（子串）匹配；未来可升级为图/时间窗
public struct MatchSpec {
    public var priority: Int64 = 0         // OQ5：越大越优先；同优先级按注册序
    public var sequence: Array<EventCondition>  // 有序；单元素即「存在即命中」
    public var requireAll: Bool = true     // true: 序列需连续匹配；false: 各条件独立「存在」
}

/// 修复样例（与 FaultPattern 一一绑定）
public struct RepairSample {
    public var rootCause: String
    public var fixSuggestion: FixSuggestion
    public var candidateCode: String       // 仓颉参考修复片段（文本）
    public var relatedInfo: Array<RelatedInfo>
    public var location: Option<Span>      // 主要错误位置（由命中事件 loc 构造）
}

/// 故障模式
public struct FaultPattern {
    public var id: String                  // 如 "RT-ARRAY-OOB"
    public var category: ErrorCategory     // 复用 diagnostics.ErrorCategory
    public var severity: Severity          // 复用 diagnostics.Severity
    public var title: String
    public var description: String
    public var matchSpec: MatchSpec
    public var repair: RepairSample
}

/// 正式故障库（OQ4 确认：内嵌为代码常量，确定性加载，无 IO）
public class FormalLibrary {
    public static let PATTERNS: Array<FaultPattern> = [
        arrayOutOfBoundsPattern(),   // RT-ARRAY-OOB   Runtime
        typeMismatchPattern(),       // TP-TYPE-MISMATCH Type
        useAfterMovePattern(),       // RT-USE-AFTER-MOVE Runtime
        nonExhaustiveMatchPattern()  // SE-NON-EXHAUSTIVE-MATCH Sema
    ]
    public static func getPattern(id: String): Option<FaultPattern> { /* 线性查找 */ }
}
```

**首批 4 类种子（F-P1-3，取自《覆盖缺口清单.md》真实场景）的 MatchSpec 要点**：

| 模式 id | category | matchSpec（本迭代朴素实现） |
|---|---|---|
| `RT-ARRAY-OOB` | Runtime | 存在 `MachineEvent` 使 `exceptionType == "ArrayIndexOutOfBounds"`（或 `kind=="array-access"` 且 `hasException`） |
| `TP-TYPE-MISMATCH` | Type | 存在 `MachineEvent` 使 `exceptionType == "TypeMismatch"`（或 `kind ∈ {"var-bind","call"}` 且 symbols 源/目标 `type` 不等） |
| `RT-USE-AFTER-MOVE` | Runtime | 序列：`ownership-transfer(move)` 事件（或 `var-bind`）+ 同 `symbolName` 的后续 `use` 事件（本迭代经 `exceptionType=="UseAfterMove"` 触发，序列能力已就绪供 P2 升级） |
| `SE-NON-EXHAUSTIVE-MATCH` | Sema | 存在 `MachineEvent` 使 `exceptionType == "NonExhaustiveMatch"`（或 `kind=="branch"` 且 `negate` 检测缺默认臂） |

> 说明：P0/P1 的种子主要靠 `exceptionType` 命中（合成 Trace 天然以 `exception` 收尾），**确定性最强**；`sequence`/`negate`/`symbolType` 等高级表达已在 `MatchSpec` 中就绪，供 P2 真实语义事件填充后升级为时间序/类型序逻辑。

### 3.6 pattern_matcher（`local_diagnostic_lib.pattern_matcher`）

```cangjie
package compiler_diagnostic.local_diagnostic_lib

import compiler_diagnostic.semantic_trace.Trace
import compiler_diagnostic.diagnostics.Span
import compiler_diagnostic.diagnostics.Severity
import compiler_diagnostic.diagnostics.ErrorCategory
import compiler_diagnostic.diagnostics.FixSuggestion
import compiler_diagnostic.diagnostics.RelatedInfo

/// 单命中确定性结果（对齐需求 F-P1-2）
public struct MatchResult {
    public var matched: Bool
    public var patternId: Option<String>
    public var location: Option<Span>
    public var severity: Option<Severity>
    public var category: Option<ErrorCategory>
    public var rootCause: Option<String>
    public var fixSuggestion: Option<FixSuggestion>
    public var candidateCode: Option<String>
    public var relatedInfo: Array<RelatedInfo>
    public init() { /* 未命中默认值：matched=false，其余 None/空 */ }
}

public struct MatchedFault {
    public var pattern: FaultPattern
    public var atEvent: MachineEvent   // 命中点事件（用于构造 location）
}

public class PatternMatcher {
    /// 朴素序列/子串匹配；OQ5 确定性：按 priority 降序 + 注册序取首个命中
    public static func match(trace: Trace): MatchResult {
        // 1) 取 FormalLibrary.PATTERNS，按 (priority desc, 注册序) 排序（排序结果稳定）；
        // 2) 遍历每个 pattern.matchSpec：对 machineEvents（+ 未来 semanticEvents）做序列/存在匹配；
        // 3) 首个命中 -> 由 atEvent.loc 构造 Span -> 填充 MatchResult；
        // 4) 全不中 -> MatchResult()（matched=false）。
    }

    /// 全部命中（供扩展/调试；本迭代调度器走 match）
    public static func matchAll(trace: Trace): Array<MatchedFault> { /* 同上但不早停 */ }
}
```

**算法说明**：本迭代为**朴素线性扫描 + 子串/序列匹配**（O(n·m)，n=事件数，m=规则数）。未来可升级为 Aho-Corasick / 时间窗 / 图匹配，接口不变。

## 4. 并发与错误策略

- **并发模型**：P0/P1 全程**单线程、同步、确定性**。无需 `spawn`/`Future`/`Mutex`。未来大 Trace 并行扫描可后置（接口不变）。
- **错误处理策略（确定性、可降级）**：
  - 控制流错误用 `Result<T, String>`（serde 加载/导出、scheduler 编排），不抛异常做正常分支。
  - `cjpm test` 测试场景用 `@Expect` 断言 `Result.isOk()`/`isErr()`。
  - **未命中可降级**（NF-3 / OQ6）：`diagnose` 成功分析但无覆盖时，输出「暂未覆盖」提示 + 回退原始信息（取自 `trace` 首个 `exception` 与 `program.entry`），**进程不崩溃**。
  - **退出码约定**（OQ6 收口）：`diagnose` 分析成功（命中或未命中）→ `0`；仅 I/O、解析、版本不兼容错误 → `2`。`run` 导出成功 → `0`，失败 → `2`。
  - **禁止**：AI / 网络 / 随机 / 时间相关不确定因素（NF-1/NF-2）。

## 5. 依赖与 FFI 边界

- **依赖**：本迭代仅用 `std`（`std.fs` 文件读写、`std.collection.*`、`std.result.Result`）。**不引入新依赖**，不依赖 stdx（stdx 仅作 vendored 兼容保留）。
- **C FFI**：本迭代**无 C FFI / `foreign` / `CFunc` / 指针**边界。语义事件层真实埋点（P2）可能涉及编译器内部，但属后续迭代，不在本设计范围。
- **版本/平台风险**：目标 `x86_64-w64-mingw32`（cjnative 动态 stdx）。`std.result.Result` 若 1.1.3 路径不符，按 §3.3 退路处理。切换 SDK 后先 `rm -rf target`。
- **确定性补充**：`schemaVersion` 与 `generator` 中的 SDK 版本来自常量，不取运行时环境动态值，避免序列化结果随环境漂移。

## 7. 开放问题逐条回应（OQ1–OQ6，本设计明确决策）

- **OQ1（P0 `run` 的 Trace 来源）**：确认采用「务实静态合成」——`event_emitter.scanSourceToTrace(file)`（轻量关键字/结构启发式扫描源文件）+ `constructSampleTrace(kind)`（受控样例）。**真实运行时插桩属 P2**，本设计不依赖任何尚不存在的 JVM/VM 埋点；`event_emitter` 内部实现可在 P2 无缝替换为真实捕获，对外接口（`scanSourceToTrace`/`buildFromEvents`）不变。

- **OQ2（性能基线门禁与子命令共存）**：确认——**`main.cj` 默认路径（无子命令）字节级保留**，仍执行 `parseArgs + generateSampleDiagnostics + 输出 + PerfBenchmark`，`cjpm run`（无参）即可稳定验证 A3。`run`/`diagnose` 作为 `dispatchSubcommand` 识别的子命令，**不进入基准路径**、不触发 `PerfBenchmark`。可选后续加显式 `benchmark` 子命令别名（非破坏性）。此设计零回归风险。

- **OQ3（语义事件层预留程度）**：确认接受 P0 仅留空壳——`SemanticEvent` 结构在 Schema 中**完整定义**，`Trace.semanticEvents: Array<SemanticEvent>` 本迭代允许为空数组；P2 填充真实语义事件，加载/序列化已兼容非空。

- **OQ4（故障模式库存储形态）**：确认内嵌为**代码常量**（`FormalLibrary.PATTERNS`，确定性加载，无 IO、无随机）。导入/导出分享（架构愿景 §7）留后续迭代；因 `FaultPattern`/`MatchSpec` 已设计为可序列化结构，未来导出为 JSON 资源零成本。

- **OQ5（多模式命中确定性选取）**：确认规则——`MatchSpec.priority: Int64`（默认 0，越大越优先）+ **注册顺序**为次级键；`PatternMatcher.match` 按 `(priority desc, 注册序)` 稳定排序后取**首个命中**，结果确定性。多命中全集由 `matchAll` 提供（本迭代调度器用 `match`）。

- **OQ6（未命中回退信息来源与格式）**：确认——回退文案源自 `Trace` 首个 `exception` 事件（`type`+`message`）与 `program.entry`；格式示例：`"本地故障模式库暂未覆盖该故障 (exception.type=<T>, message=<M>, program=<entry>)"`。退出码：分析成功（命中或未命中）→ `0`；仅 I/O/解析/版本不兼容 → `2`（OQ6「退出码明确」）。`diagnose` 未命中时进程不崩溃、输出明确提示。
