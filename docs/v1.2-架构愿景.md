# compiler_diagnostic 架构设计文档（v1.2-design）

> 版本：v1.2-design ｜ 状态：本迭代落地目标 ｜ 提出人：用户
> 核心变更：**移除全部 AI 相关能力**，转向基于执行轨迹 Trace 的纯本地确定性编程诊断。

---

## 1. 设计总览

### 核心设计原则
- **Trace 为一等公民资产**：Trace 是版本化、可序列化文档，支持程序运行时在线生成，也支持离线加载历史 Trace 做故障复盘；Trace 生成和故障诊断完全解耦。
- **Trace 分为两层**：
  - 机器执行层：step_id、源码位置、栈帧快照、变量/符号值、执行路径、异常信息。回答：程序执行到哪里、变量是什么、抛出了什么异常。
  - 仓颉语言语义事件层：条件求值、循环进入/迭代、函数调用返回、符号绑定、类型推导、所有权转移、模式匹配分支、模块导入等。回答：程序逻辑层面发生了什么行为。
- **完全本地确定性诊断**：全部诊断逻辑运行在本地，不依赖 AI、不依赖网络。基于 Trace 对本地故障模式库做模式匹配，输出错误位置、根因描述、修复参考样例。
- **在线、离线两套输入路径，复用同一套诊断逻辑**：
  - 在线路径：运行仓颉源码，实时采集事件生成 Trace。
  - 离线路径：直接读取磁盘上已保存的 Trace 文件，不需要原始程序复现故障。
- **故障模式库可人工维护扩展**：故障模式库为静态可编辑资源，由人新增、编辑、删除故障模式与修复样例；模式库与 Trace Schema 配套，定义 Trace 事件特征与对应修复方案。
- **可降级**：核心诊断能力不依赖任何外部服务；没有网络也可以完整工作。

## 2. 核心概念

### 2.1 Trace（执行追溯记录）
- 持久化文档，格式：`.trace.json`，自带 Schema 版本号，保障格式迭代兼容。
- **机器执行层**：step_id、源码位置、栈帧快照、变量/符号值、执行路径、异常信息。
- **语义事件层（仓颉特有）**：条件求值、循环进入/迭代、函数调用返回、符号绑定、类型推导、所有权转移、模式匹配分支、模块导入等。

### 2.2 本地故障模式 & 修复样例库
- 完全本地静态资源。
- **故障模式**：描述一组 Trace 事件特征序列。例如：循环迭代事件 + 数组下标越界访问事件。匹配输入就是完整 Trace 事件序列与状态快照。
- **修复样例**：与故障模式一一绑定，包含：故障现象描述、根因说明、仓颉参考修复代码片段。
- **模式匹配引擎**：接收完整 Trace，遍历全部故障模式做匹配；输出命中结果以及对应的修复样例。
- **扩展方式**：人工编辑维护故障库，新增故障模式、修复样例；不需要 AI 自动生成。

## 3. 系统模块结构

```
compiler_diagnostic
├── diagnostic_core           # 原有：编译器核心诊断、错误收集、AST/IR处理（保留，v1.1.x 的 200 码体系）
├── semantic_trace            # Trace 子系统
│   ├── trace_schema          # Trace 版本化数据模型定义
│   ├── event_emitter         # 事件发射器：埋点采集机器事件、仓颉语义事件
│   ├── serde                 # Trace 序列化 / 反序列化
│   └── trace_util
│       └── trace_tools       # Trace 查询、切片、Trace-Diff 对比工具
├── local_diagnostic_lib      # 本地确定性诊断库（核心）
│   ├── formal_library        # 正式故障模式库 + 修复样例库，人工维护编辑
│   ├── pattern_matcher       # Trace 模式匹配引擎
│   └── repair_resource       # 故障描述、修复代码片段资源
├── diagnostic_scheduler      # 诊断调度中枢：统一管理在线/离线流程
└── cli                       # 命令行入口
```

## 4. 完整业务主流程

```
输入二选一：
  ① 在线：运行仓颉源码 → event_emitter 采集事件 → 生成完整 Trace
  ② 离线：从磁盘加载历史 .trace.json 文件
          ↓
Trace 送入【pattern_matcher 模式匹配引擎】，读取【formal_library 正式故障库】
         ↓
  ├─ ✅ 命中故障模式：输出错误源码位置、故障描述、根因、参考修复样例。流程结束。
  └─ ❌ 没有命中任何故障模式：提示「本地故障模式库暂未覆盖该故障」，仅输出原始运行/编译错误信息。流程结束。
```

## 5. CLI 命令设计

```bash
# 运行仓颉源码，导出完整 Trace 到本地文件
compiler_diagnostic run test.cj --export-trace fault.trace.json

# 离线诊断，读取 Trace 文件做分析，完全本地运算
compiler_diagnostic diagnose --trace fault.trace.json
```

## 6. 分阶段迭代计划

### P0 Trace 底座（最高优先级）
- [P0] 定义带版本号的 Trace Schema，实现机器层事件数据模型；预留语义事件字段。
- [P0] 实现 semantic_trace 模块：序列化、反序列化；Trace 导出、文件加载。
- [P0] CLI 实现 run、diagnose 基础命令。
- [P0] 搭建 diagnostic_scheduler 调度器基础框架。

### P1 落地本地确定性诊断核心
- [P1] 设计故障模式数据模型、修复样例数据模型。
- [P1] 实现 local_diagnostic_lib：pattern_matcher 模式匹配引擎。
- [P1] 录入首批仓颉典型故障模式：数组越界、类型不匹配、所有权误用、模式匹配遗漏分支等。
- [P1] 跑通完整本地诊断链路：输入 Trace，输出错误位置、根因、修复样例。

### P2 补齐仓颉语义 Trace 能力
- [P2] 在 AST/IR 执行流程埋点，event_emitter 输出仓颉特有语义事件。
- [P2] trace_util 实现 Trace 查询、切片、Trace-Diff 两次执行对比。

### P4 测试与文档
- [P4] 单元测试覆盖场景：
  - Trace 正常生成、保存、离线加载。
  - Trace 命中已有故障模式，输出修复建议。
  - Trace 未命中故障库，输出提示信息。
- [P4] 编写文档：Trace 格式规范、故障模式编写维护手册、项目架构文档。

## 7. 扩展方向
- 故障模式库支持导入/导出，方便模式库分享。
- Trace 敏感字段掩码，对变量快照中的敏感数据做脱敏。
- 增加简单配置文件，管理 Trace 输出路径、模式库路径。

## 8. 与现有 v1.1.x 的关系（落地约束）
- `diagnostic_core`（现有 `src/diagnostics`，200 码 + `ErrorMeta`/`Span`/`FixSuggestion`/`Candidate` 等）**保留不动**，作为「编译期静态诊断」通道。
- v1.2 在现有包之上新增 `semantic_trace` / `local_diagnostic_lib` / `diagnostic_scheduler` 三个顶层模块，并在 `cli` 增加 `run`/`diagnose` 子命令。
- 风格对齐：错误/严重程度/修复建议沿用 `Severity`（`Fatal/Error/Warning`）、`Span`、`FixSuggestion`、`Candidate` 的数据形态；Trace 的 JSON 序列化参考 `src/output/JSONSchema.cj` + `JSONOutput.cj`。
- 性能基线约束（`main.cj` 的 `PERF_BASELINE` 回归门禁）与 cjlint 门禁（MANDATORY=0、warning 收敛）在本迭代仍须保持通过。
