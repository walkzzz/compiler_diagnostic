## 2. 与《覆盖缺口清单.md》的对照

缺口清单的核心结论（基准 200 码时）：**整体覆盖约 60–70%**，最缺的是 **Sema / Type / Codegen / Runtime 的细节场景**；并指出两类比"多加码"更关键的判断：

1. **结构性缺口**（主/次 spans、related notes、宏/泛型展开回溯、多候选 suggestions）决定"诊断质量"，比码数更重要；
2. **开发工具链支持"已足够"** —— 渲染/LSP/文档/CI 均可基于现有 API 建设。

本扩展同时回应了这两点：先把码补齐到生产级，再用 VS Code 通用插件把"开发工具映射"做扎实；结构性字段（spans/notes）的单点改造留作后续 B 方案（见 §6）。

### 2.1 缺口清单 P0/P1/P2 → 本次新增类别映射

| 缺口清单位置 | 缺口项 | 本次落点（类别/前缀） |
|---|---|---|
| 1.3 Sema P0 | trait 实现缺方法、闭包捕获环境、重载无可用候选 | `Trait`(E03) / `Borrow`(E04) |
| 1.4 Type P0 | 编译期 const 求值/溢出、Option/可空解包 | `Type`(E20) 既有 + `Generic`(E06) 单态化 |
| 1.6 Codegen P0 | 泛型单态化失败、链接器执行失败、builtin 目标不支持 | `Generic`(E06) / `Linker`(E13) / `Backend`(E11) |
| 1.7 Runtime P0 | 双重释放、堆 use-after-free | `Mem`(E52) |
| 1.2 Parser P1 | 模式语法、结构体/枚举/接口成员语法、lambda、字符串插值 | `Parser`(E01) 既有 + `Macro`(E02) |
| 1.3 Sema P1 | 默认/命名参数、可变性传播、async 语义 | `Sema`(E10) / `Concurrency`(E51) |
| 1.5 Resolution P1 | glob 导入歧义、宏卫生性、可见性层级 | `Module`(E07) / `Macro`(E02) |
| 1.6 Codegen P1 | 调用约定、TLS、FFI ABI、目标 triple | `Abi`(E14) / `Tgt`(E67) |
| 1.7 Runtime P1 | actor/信道、原子误用、线程数超限 | `Concurrency`(E51) |
| 跨类 P1 | 宏/泛型展开回溯、多候选 suggestions | `Macro`(E02) / `Generic`(E06)（场景码）+ 后续 spans/notes 字段 |
| 2. 结构性 P0 | 主/次 spans、related notes | 后续 B 方案（改 `ErrorMeta`，不扩码） |
| 1.8 System P2 / 1.1 Lexer P2 | 增量缓存、远程/分布式编译、字面量细分 | `Incremental`(E61) / `Dist`(E65) / `Lexer`(E00) |

> 说明：新增 32 类并非只覆盖清单点名的场景，而是把每个子系统**常见诊断面**一并铺开（每类约 30–40 个真实场景码），从而把覆盖率从 ~65% 推到接近完整，并具备生产级冗余。

### 2.2 关于"开发工具链已足够"的落点

缺口清单判定 dev-tool 支持已足够，是因为现有 `ErrorMeta`/`code()`/`category()`/`severity()`/`template()`/`fromCode` 已能提供渲染/LSP/文档/CI 所需的一切。本交付把这一判断**产品化**：新增 `vscode-extension/`（通用插件模式），把"足够"变成"开箱即用"。

## 3. 四要素一致性保障（不靠人工、靠生成器+校验器）

每个错误码在源码中存在 **4 个同步点**，任一漏改都会破坏 `ErrorCodeCompletenessTest`：

1. 枚举变体 `VariantName`
2. META 条目 `m["Exxxx"]`
3. `code()` 的 `match` 分支 `case ErrorCode.X => "Exxxx"`
4. `all()` 的 `list.add(ErrorCode.X)`

每个 `ErrorCategory` 另有 **4 个同步点**：枚举变体 + 三处 `match(this)`（`codePrefix()`/`stage()`/`displayName()`）。

### 3.1 一致性设计

- **META 驱动访问器**：`category()`/`severity()`/`template()`/`fromCode` 全部读 META，无穷举 `switch`，因此"加码"只需新增 META，不必改访问器（唯一需要穷举 `match` 的是 `code()`，由生成器一并补充分支）。
- **单一真源生成器** `tools/gen_error_codes.py`：`CATALOG` 列出 32 类元组 `(abbr, prefix, stage, display, [(key, template, fix, severity), ...])`，变体名 = `abbr + Pascal(key)`，按唯一锚点（如 `return m`、`public static func all()`、`public func code()` 的 `match` 块）插入，**一处定义、四处同步**。
- **结构校验器** `tools/validate_error_codes.py`：纯文本解析（不依赖编译器），核对
  - META 键/码一致、`code()`→枚举+`all()`+META 一致、枚举↔`all()` 对称；
  - 每个类别四要素完整；
  - 模板无 `${` 危险字符（避免误当插值）；
  - 码值前缀一致性（`code.startsWith(cat.codePrefix())`，即 `ErrorCodeCompletenessTest` 的判定标准）；
  - 测试断言数 == 枚举变体数。
- **编译期门禁** `ErrorCodeCompletenessTest`（`src/ut/ErrorCode_test.cj`）：锁定总数 1527，并断言 `code.startsWith(prefix)`、severity ∈ {Fatal,Error,Warning}、template 非空。

## 4. 开发工具映射：VS Code 通用插件模式

设计原则：**map-driven（映射驱动），绝不硬编码错误码**。插件只读 `diagnostics-map.json`，任何新码无需改插件代码即可被识别、上色、给出修复建议。这与缺口清单"dev-tool 已足够、应基于现有 API 建设"的判断完全一致，并把"映射"做成可分发、可版本化的产物。

### 4.1 目录结构

```
vscode-extension/
├── package.json                 # 清单：语言 cangjie(.cj)、命令、设置
├── tsconfig.json                # TS 编译配置
├── language-configuration.json  # Cangjie 括号/注释配置
├── diagnostics-map.json         # ★ 错误码映射（生成器产出，1519 条）
├── src/extension.ts            # 通用适配器（无硬编码码值）
└── README.md                   # 使用说明
```

### 4.2 `diagnostics-map.json` 字段 schema

每条错误码（按 `code` 去重，8 个别名回退到规范码）形如：

```jsonc
{
  "code": "E1101",
  "variant": "BackendLlvmVerifyFailed",
  "category": "Backend",
  "severity": "Error",            // Fatal | Error | Warning
  "lspSeverity": 1,               // 1=Error, 2=Warning, 3=Info（LSP 标准）
  "editorSeverity": "error",      // vscode.DiagnosticSeverity 取值
  "actionable": true,             // 是否有可应用修复
  "template": "LLVM 校验失败：{reason}",
  "fix": "检查 {reason} 对应的源码位置并修正类型/ABI 不匹配"  // 或 null
}
```

- 当前产出：**1519 条唯一码、40 个类别**。
- 由 `tools/gen_vscode_map.py` 从扩码后的 `Diagnostics.cj` META 直接抽取，与源码单一真源同源。

### 4.3 `src/extension.ts` 适配逻辑（要点）

- `resolveSeverity(code, rawSeverity, mapEntry)`：优先级 **用户 `severityOverride`（按码前缀）> 原始 severity > map 的 `editorSeverity`**，满足按项目微调严重度的需求。
- `applyDiagnostics(diagnostics: RawDiagnostic[])`：把 `{code, severity, message, span, fix, rootCause}` 映射为 `vscode.Diagnostic[]`，按文件定位、着色、附加修复动作（CodeAction）。
- 命令：`cangjie.applyDiagnosticMap`（从选区/JSON 应用映射）、`cangjie.openDiagnosticDoc`（Webview 打开诊断文档）。
- 设置：`cangjie.diagnostics.mapPath`、`cangjie.severityOverride`、`cangjie.autoApplyOnOutput`。
- **关键**：插件不认识任何一个具体 `Exxxx`，所有行为由 `diagnostics-map.json` 驱动——未来再加码，只需重新生成 map 并 reload。

### 4.4 与 IDE / LSP / CI / 文档 的复用关系

- **IDE 插件** ↔ **LSP**：`lspSeverity` 字段直接对接 LSP `DiagnosticSeverity`，VS Code 只是其中一个消费端。
- **CI**：`diagnostics-map.json` 可作为 CI 门禁的"已知诊断白/黑名单"数据源（如禁止某前缀 `Fatal` 合入）。
- **文档**：同一 map 可驱动 `docs/` 自动生成"错误码速查表"，保证文档与代码同源。

## 6. 后续建议（与缺口清单方向一致）

1. **B 方案（杠杆最大）**：给 `ErrorMeta` 增 `spans: Array<Span>`、`notes: Array<Note>` 字段，让 `toDiagnostic()`/`toLsp()` 输出主/次位置与关联说明——这是"诊断质量"项目真正的胜负手，且可独立于扩码推进。
2. **A 方案收尾**：本交付已完成 A（P0/P1/P2 全覆盖），但建议用真实 `cjc` 报错样本回灌，校准模板措辞与严重度。
3. **C 方案**：建真实 `cjc` 诊断 → `E` 码桥接表，让真实报错能吐规范码（缺口清单确认此层仍缺失）。
4. **插件自动化**：把 `gen_vscode_map.py` 接入 `cjpm build` 后钩子，map 与源码始终同源。
