## 1. 目标与范围

### 1.1 目标
移除 v1.1.x 的全部 AI 能力，转向**基于执行轨迹 Trace 的纯本地确定性诊断**：在线运行仓颉源码采集 Trace，或离线加载 `.trace.json`，用本地故障模式库做模式匹配，输出「错误位置 + 根因 + 修复样例」，全程不依赖网络 / AI。本迭代只交付 v1.2 的**最小闭环**。

### 1.2 In-Scope（本迭代必须交付）
- **P0**：带版本号的 Trace Schema（机器层 + 预留语义事件层字段）；`semantic_trace` 的 serde 与文件导出/加载；CLI `run`/`diagnose` 基础命令；`diagnostic_scheduler` 调度框架。
- **P1**：故障模式 + 修复样例数据模型；`pattern_matcher` 引擎；首批故障模式种子（≥4 类：数组越界、类型不匹配、所有权误用、模式匹配遗漏分支，取自《覆盖缺口清单.md》真实场景）；跑通「输入 Trace → 输出位置/根因/修复样例」或「未命中 → 提示」的完整链路。

### 1.3 Out-of-Scope（本迭代不做，仅预留）
- **P2**：语义事件层真实埋点（`event_emitter` 的仓颉语义事件采集）；`trace_tools` 的查询/切片/Trace-Diff（留接口或最小占位即可）。
- 故障模式库导入/导出分享、Trace 敏感字段掩码、配置文件管理（架构愿景 §7 扩展方向，后续迭代）。
- 真实 `cjc` 前端各 phase 报错点 1:1 映射（见《覆盖缺口清单.md》结论，非本迭代目标）。
- 不改动 / 不删除现有 `diagnostic_core`（200 码体系），其作为「编译期静态诊断」通道保留。

## 3. 功能需求清单（按 P0 / P1 / P2 标注）

> 说明：以下用「字段规格表」描述数据模型（属规格，非实现代码），编码阶段据此落地仓颉类型。

### P0 —— Trace 底座

#### F-P0-1  带版本号的 Trace Schema（机器层完整 + 语义事件层字段预留）
- **描述**：定义 `.trace.json` 的版本化根结构，机器执行层字段本迭代可完整填充；仓颉语义事件层在 Schema 中**定义结构并预留字段**（P0 允许为空数组，P2 填充）。
- **根结构字段**：
  | 字段 | 类型 | 说明 |
  |---|---|---|
  | `schemaVersion` | String | 版本号（建议语义化如 `"1.0.0"`）；加载时校验 MAJOR 兼容，不兼容则报错拒绝 |
  | `generator` | Object | 可选元信息 `{ tool, version, sdk }`，便于溯源 |
  | `program` | Object | 程序标识 `{ entry: String, args: Array<String> }` |
  | `machineEvents` | Array\<MachineEvent\> | 机器执行层事件序列（本迭代实现） |
  | `semanticEvents` | Array\<SemanticEvent\> | 仓颉语义事件层（P0 预留结构，可空数组） |
- **MachineEvent 字段**：
  | 字段 | 类型 | 说明 |
  |---|---|---|
  | `stepId` | Int64 | 全局递增步骤序号 |
  | `kind` | String | 事件类型（基础集：`"step"`/`"call"`/`"return"`/`"branch"`/`"array-access"`/`"var-bind"`/`"exception"`；语义类型见下） |
  | `loc` | SourceLoc | 复用 `diagnostics.SourceLoc` |
  | `stack` | Array\<StackFrame\> | 轻量栈帧快照 `{ function: String, loc: SourceLoc }` |
  | `symbols` | Array\<SymbolValue\> | 变量/符号值快照 `[{ name, type, valueRepr }]` |
  | `path` | String | 执行路径标识（如 `"then"`/`"else"`/循环迭代号），供模式匹配做路径特征 |
  | `exception` | Option\<ExceptionInfo\> | `{ type: String, message: String }`；无异常为 `None` |
- **SemanticEvent（预留结构，P2 填充）字段**：
  | 字段 | 类型 | 说明 |
  |---|---|---|
  | `stepId` | Int64 | 步骤序号 |
  | `kind` | String | 语义类型：`"conditional-eval"`/`"loop-enter"`/`"loop-iter"`/`"call-return"`/`"symbol-bind"`/`"type-infer"`/`"ownership-transfer"`/`"match-arm"`/`"module-import"` |
  | `loc` | SourceLoc | 位置 |
  | `detail` | Object | 结构化信息（类型/值/分支等） |
  | `relatedSpan` | Option\<Span\> | 关联源码范围 |
- **验收信号**：存在一个可被 serde 消费的稳定 Schema 结构与版本号字段；`semanticEvents` 在本迭代可合法为空。

#### F-P0-2  `semantic_trace` 序列化/反序列化 + 文件导出/加载
- **描述**：实现 Trace 的 JSON 序列化与反序列化（参考 `JSONSchema.cj`/`JSONOutput.cj` 风格）；提供「导出到 `.trace.json`」与「从 `.trace.json` 加载」能力。
- **输入**：内存中 Trace 对象 / 磁盘 `.trace.json` 路径。
- **输出**：序列化后的 JSON 文本 / 反序列化后的 Trace 对象。
- **必须保证**：round-trip 一致（序列化→写盘→读盘→反序列化 == 原对象关键字段）；加载时校验 `schemaVersion` 的 MAJOR 兼容性，不兼容时返回明确错误而非静默损坏。
- **验收信号**：存在程序化构造 Trace 并写盘、再读盘还原的 API（支撑 UT 场景 ① 与 ②）。

#### F-P0-3  CLI `run` / `diagnose` 基础命令
- **描述**：在 `cli` 增加两个子命令，不破坏现有 `--diagnostic=json|lsp|text` 样例打印与性能基准路径（见 OQ2）。
- **命令契约**：
  ```bash
  # 运行仓颉源码，导出完整 Trace 到本地文件
  compiler_diagnostic run <source.cj> --export-trace <out.trace.json>
  # 离线诊断，读取 Trace 文件做分析，完全本地运算
  compiler_diagnostic diagnose --trace <in.trace.json>
  ```
- **输入**：`run` 接收源文件路径 + 导出路径；`diagnose` 接收 trace 文件路径。
- **输出**：`run` 产出非空 `.trace.json`；`diagnose` 输出诊断（命中：位置/根因/修复样例；未命中：提示信息，见 F-P1-4）。
- **验收信号**：两命令可被 `main` 的子命令分发识别并独立执行（见 F-P0-4 与 OQ1）。

#### F-P0-4  `diagnostic_scheduler` 调度框架
- **描述**：诊断调度中枢，统一管理在线/离线两条输入路径，本迭代先搭**基础框架**并接入 P0/P1 能力。
- **职责**：解析子命令与参数 → 校验 → 分发到 `semantic_trace`（加载/导出）与 `local_diagnostic_lib`（P1 接入 `pattern_matcher`）。
- **在线路径**：P0 以「最小可运行 harness」产出 machine-layer Trace（完整运行时插桩留 P2，见 OQ1）；离线路径直接读盘。
- **验收信号**：存在统一的调度入口，能根据输入（源文件 / trace 文件）走到正确流程并产出确定结果。

### P1 —— 本地确定性诊断核心

#### F-P1-1  故障模式 + 修复样例数据模型
- **描述**：定义故障模式与修复样例的结构，二者一一绑定，作为 `formal_library` 的可维护静态资源。
- **FaultPattern 字段**：
  | 字段 | 类型 | 说明 |
  |---|---|---|
  | `id` | String | 唯一标识（如 `"RT-ARRAY-OOB"`） |
  | `category` | ErrorCategory | 复用 `diagnostics.ErrorCategory` |
  | `severity` | Severity | 复用 `diagnostics.Severity` |
  | `title` | String | 简短标题 |
  | `description` | String | 故障现象描述 |
  | `matchSpec` | MatchSpec | 匹配特征：事件序列/谓词（确定性规则，**禁止**引入 AI/ML/网络/随机） |
  | `repair` | RepairSample | 对应修复样例 |
- **RepairSample 字段**：
  | 字段 | 类型 | 说明 |
  |---|---|---|
  | `rootCause` | String | 根因说明 |
  | `fixSuggestion` | FixSuggestion | 复用 `diagnostics.FixSuggestion` |
  | `candidateCode` | String | 仓颉参考修复代码片段（文本） |
  | `relatedInfo` | Array\<RelatedInfo\> | 可选，复用 `diagnostics.RelatedInfo` |
  | `location` | Option\<Span\> | 主要错误位置（由匹配到的 Trace 事件 `loc` 构造） |
- **验收信号**：模型可被编码为静态资源并被 `pattern_matcher` 加载消费。

#### F-P1-2  `pattern_matcher` 模式匹配引擎
- **描述**：接收完整 Trace（machineEvents + semanticEvents），遍历 `formal_library` 全部 FaultPattern 做确定性匹配，输出结果。
- **输入**：完整 Trace。
- **输出**（MatchResult）：
  | 字段 | 类型 | 说明 |
  |---|---|---|
  | `matched` | Bool | 是否命中 |
  | `patternId` | Option\<String\> | 命中模式 id |
  | `location` | Option\<Span\> | 错误源码位置 |
  | `severity` | Option\<Severity\> | 严重度 |
  | `category` | Option\<ErrorCategory\> | 类别 |
  | `rootCause` | Option\<String\> | 根因 |
  | `fixSuggestion` | Option\<FixSuggestion\> | 修复建议 |
  | `candidateCode` | Option\<String\> | 参考修复代码 |
  | `relatedInfo` | Array\<RelatedInfo\> | 关联信息 |
- **确定性要求**：相同 Trace 输入 → 相同输出；无随机/网络/时间依赖；多模式可能同时命中时按固定顺序/优先级确定性选取（OQ5）。
- **验收信号**：引擎对种子模式可重复产出一致结果。

#### F-P1-3  首批故障模式种子（≥4 类，取自《覆盖缺口清单.md》真实场景）
- **描述**：录入以下 4 类典型故障模式（场景映射覆盖缺口清单中已标注的真实编译器诊断面）。
  1. **数组越界（ArrayOutOfBounds）** — `Runtime` 类。Trace 特征：`array-access` 事件且 `exception.type == "ArrayIndexOutOfBounds"`（或下标 ≥ 长度）。场景源自《覆盖缺口清单.md》Runtime `E5002 数组越界`。修复样例：边界检查 / 改用安全下标访问。
  2. **类型不匹配（TypeMismatch）** — `Type` 类。Trace 特征：赋值/传参事件中源类型 ≠ 目标类型（如 `String` vs `Int`，对应 `AppSupport.cj` 中 `reportTypeMismatch` 样例）。场景源自《覆盖缺口清单.md》Type `E2001 类型不匹配`。修复样例：显式转换 / 修正类型注解。
  3. **所有权误用（UseAfterMove）** — `Runtime` 类。Trace 特征：`ownership-transfer`(move) 事件后，同一符号出现 use 事件。场景源自《覆盖缺口清单.md》Runtime `E5011 move 后使用`。修复样例：避免 move 后使用 / 改用 Copy 或借用。
  4. **模式匹配遗漏分支（NonExhaustiveMatch）** — `Sema` 类。Trace 特征：`match` 表达式求值事件中，输入值未命中任何 `match-arm` 事件（分支集合不覆盖该值），抛异常或默认臂缺失。场景源自《覆盖缺口清单.md》Sema `E1014 match 穷尽` / Parser `if/match/while` 缺臂。修复样例：补全分支 / 增加通配臂。
- **验收信号**：4 类模式均能被对应构造的 Trace 命中并输出修复样例（支撑 UT 场景 ③）。

#### F-P1-4  完整诊断链路（命中 → 输出；未命中 → 提示）
- **描述**：`diagnostic_scheduler` 串联「加载 Trace → pattern_matcher → 输出」。
  - ✅ **命中**：输出错误源码位置（`Span`）+ 故障描述 + 根因 + 参考修复样例（`FixSuggestion` + `candidateCode`）+ 可选关联信息。
  - ❌ **未命中**：输出提示「本地故障模式库暂未覆盖该故障」，并回退输出原始运行/编译错误信息（取自 Trace 的 `exception`/`program` 字段），进程不崩溃、退出码明确。
- **验收信号**：存在端到端可调用的诊断入口（支撑 UT 场景 ③ 与 ④，以及 CLI A5）。

### P2 —— 仅预留（本迭代不强制实现完整埋点）

#### F-P2-2  `trace_tools` 查询 / 切片 / Trace-Diff
- `semantic_trace/trace_util/trace_tools` 的查询、切片、两次执行对比。本迭代可只留接口或最小占位。

## 4. 非功能需求

- **NF-1 确定性（强制）**：全部诊断逻辑本地、确定性；相同 Trace → 相同输出；禁止 AI / 网络 / 随机 / 时间相关不确定因素。模式匹配顺序/优先级固定（见 OQ5）。
- **NF-2 离线 / 无网络 / 无 AI（强制）**：核心诊断能力不依赖任何外部服务；无网络环境可完整工作；彻底移除 v1.1.x 的 AI 路径。
- **NF-3 可降级**：无网络不影响核心能力；当无故障模式命中时，优雅回退输出原始错误信息与提示，不崩溃。
- **NF-4 性能门禁不回归（强制）**：`main.cj` 的 `PERF_BASELINE`（`BenchmarkResult(0.001, 0.041)`，判定 `timeRatio<=1.05` 通过）在本迭代仍须通过；新增模块不得导致基准回归。具体门禁命令见 §5.A3 与开放问题 OQ2。
- **NF-5 风格对齐（强制）**：错误位置/严重度/修复建议/候选/关联信息复用 §2.3 所列现有类型，不另起一套；JSON 序列化风格参考 `JSONSchema.cj`/`JSONOutput.cj`。
- **NF-6 cjlint 门禁（强制）**：`cjlint` 报告 `MANDATORY=0` 且**无 error 级**问题；warning 不强制归零但应保持收敛趋势、不新增 blocking 项。

  - 对应需求：§2 环境约束、F-P0-1~4、F-P1-1~4。

- [ ] **A2 `cjlint` MANDATORY=0、无 error**
  - 命令：`cjlint`
  - 预期：报告 `MANDATORY=0`；无 error 级条目（warning 收敛、无 blocking）。
  - 对应需求：§4.NF-6。

- [ ] **A3 性能基线门禁不回归（`PERF_BASELINE` 比对）**
  - 命令：`cjpm run`（默认/基准路径执行 `main`，运行 `PerfBenchmark` 并比对 `PERF_BASELINE`；若 dispatch 改为子命令则相应调整，见 OQ2）
  - 预期：stdout 含 `性能基准: ... (通过)`，`timeRatio<=1.05` 且 `memRatio` 通过，进程退出码 0。
  - 对应需求：§4.NF-4、§2.3。

- [ ] **A4 单元测试覆盖 4 类场景（`cjpm test` 全绿）**
  - 命令：`cjpm test`
  - 预期：退出码 0，且至少覆盖以下 4 类（落在 `src` 下既有 ut 体系，§2.4）：
    1. **Trace 正常生成并保存**：用 Trace 构造 API 生成 Trace → 序列化 → 写 `.trace.json`，文件非空且可解析。
    2. **离线加载 `.trace.json`**：读盘 → 反序列化 round-trip，关键字段一致；`schemaVersion` MAJOR 校验通过。
    3. **Trace 命中已有故障模式并输出修复建议**：用任一种子模式（§3.F-P1-3）构造 Trace → `diagnose` 输出 `location`+`rootCause`+`fixSuggestion`+`candidateCode`。
    4. **Trace 未命中故障库输出提示信息**：构造未被任何模式覆盖的 Trace → `diagnose` 输出「暂未覆盖」提示且不崩溃。
  - 对应需求：F-P0-2、F-P1-2、F-P1-4。

- [ ] **A5 CLI `run` 与 `diagnose` 端到端跑通**
  - 命令（示例形态，具体 sample 文件名以编码阶段约定为准）：
    ```bash
    compiler_diagnostic run samples/array_oob.cj --export-trace /tmp/fault.trace.json
    compiler_diagnostic diagnose --trace /tmp/fault.trace.json
    ```
  - 预期：`run` 生成非空 `.trace.json`（`schemaVersion` 正确、`machineEvents` 非空）；`diagnose` 读取后输出命中模式（错误位置/根因/修复样例）。另构造一个未命中场景验证提示分支（与 A4-④ 互证）。
  - 对应需求：F-P0-3、F-P0-4、F-P1-4。

## 6. 风险与开放问题

### 风险
- **R1 跨 SDK 残留致 `exit 127`**：已固化配方——构建前 `rm -rf target`（§2.2）。任何 CI/本地构建均需遵守。
- **R2 cjlint warning 反弹**：新增 `semantic_trace`/`local_diagnostic_lib`/`diagnostic_scheduler` 三模块不得引入 MANDATORY 违规或新增 error。
- **R3 stdx 路径耦合**：`cjpm.toml` 已相对路径引用 stdx；评委环境需提供 SDK（设 `CANGJIE_HOME`），无需预装 stdx。编码阶段不得改为绝对路径硬编码。

### 开放问题（需架构/编码专家确认，不影响本需求文档落盘）
- **OQ1 P0 `run` 的 Trace 来源机制**：完整在线插桩任意 `.cj` 需编译器/VM 埋点（属 P2）。P0 最小闭环建议：`run` 运行一个**受控 trace 样例程序**或内置 trace 构造 harness 产出 machine-layer Trace；真正的运行时插桩留 P2。需架构专家确认 `run` 的最小契约与样例载体。
- **OQ2 性能基线门禁与子命令共存**：现有 `main.cj` 默认执行 sample + `PerfBenchmark` 并据 `report.passed` 返回 0/1。新增 `run`/`diagnose` 子命令后，须保证 `PERF_BASELINE` 门禁仍可稳定验证（保留默认/基准路径？或改为 `benchmark` 子命令？）。需确认 dispatch 设计，使 A3 命令稳定可回归。
- **OQ3 语义事件层「预留」程度**：建议 P0 在 Schema 中定义 `SemanticEvent` 结构并允许空数组；P2 才填充。需确认是否接受 P0 仅留空壳字段。
- **OQ4 故障模式库存储形态**：本迭代建议内嵌为代码常量/资源，便于确定性加载；导入/导出分享（架构愿景 §7）留后续。需确认。
- **OQ5 多模式命中时的确定性选取规则**：建议固定注册顺序 + 可选 `priority` 字段，确定性选取首个命中。需在 `pattern_matcher` 中明确。
- **OQ6 未命中时「原始运行/编译错误信息」的来源字段**：建议取自 Trace 的 `exception`/`program` 字段；需明确字段与回退文案格式。
