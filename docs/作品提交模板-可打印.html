一、项目概述

1. 项目一句话定位

本项目面向仓颉编译器开发者，提供结构化的诊断输出能力，解决仓颉原生开发中错误信息不清晰、缺少修复建议、IDE 集成困难的痛点，可大幅提升开发者排错效率与编码体验。

2. 项目开发背景

  • 错误信息格式不统一，缺少结构化字段
  • 缺少修复建议，开发者需自行排查问题
  • JSON 输出不符合 LSP 规范，IDE 集成困难
  • 错误码体系不完善、不稳定，回归测试困难

3. 项目核心目标

  • 基础功能目标：实现 Parser/Sema 诊断字段结构化、JSON 输出符合 LSP 规范
  • 进阶创新目标：提供修复建议、候选符号、性能基准测试框架

二、需求分析与适用人群

1. 目标用户精准定位

  • 仓颉语言开发者（核心用户）
  • IDE 插件开发者（二次开发）
  • AI 编程助手开发者（集成调用）
  • 仓颉编译器团队成员（参考实现）

2. 行业开发痛点与解决方案

痛点解决方案
错误信息不清晰结构化字段：code / severity / message / span / fix / candidates
缺少修复建议FixSuggestion 模块提供可执行的修复建议

三、作品核心能力与功能设计

1. 基础通用能力

（1）能力一：错误码体系
定义 1519 个标准化错误码（E00–E90 共 40 类：Lexer/Parser/Macro/Sema/Type/Backend/Build/Lsp…System）。采用 `E` + 2 位类别前缀 + 2 位序号 的编码规范，零孤儿、零畸形，97% 修复覆盖。通过 `ErrorCode` 枚举访问。

（2）能力二：结构化诊断消息
DiagnosticMessage 包含 code / severity / message / span / fix / related / candidates。通过 DiagnosticBuilder 链式构建，提供完整错误上下文。

2. 创新特色能力

（1）创新点一：LSP 兼容 JSON 输出
诊断输出符合 Language Server Protocol 规范（`range.character` 而非 `column`、数字 `severity`、`codeAction` 一键修复），可直接对接 IDE；唯一提供 LSP 兼容输出的诊断库。

（2）创新点二：修复建议 + 候选符号 + 根因归因
FixSuggestion 提供可执行修复；candidates 携带符号类型（如 `var1(variable)`）；rootCause 提供结构化根因，便于 AI 助手归因。

四、仓颉语言核心特性应用

  • Option 类型：使用 `Option` / `Option>` 表示可选字段，避免 null。
  • Builder 模式：DiagnosticBuilder 链式调用，API 易用。
  • 枚举 match 表达式：ErrorCode 使用 match 返回 code/description，编译期类型安全。
  • 多后端 / 跨平台：基于 cjnative 1.1.3，纯仓颉实现，无外部依赖。

五、库性能与兼容性设计

  • 性能优化：PerfBenchmark 模块提供性能基准测试框架，`compareWithBaseline` 固化 ≤1.05× 时间/内存门禁。
  • 兼容性：支持 Cangjie 1.1.3 (STS/cjnative)。
  • 稳定性与容错：Option<T> 表示可选字段；JSON 序列化失败降级为文本输出。
