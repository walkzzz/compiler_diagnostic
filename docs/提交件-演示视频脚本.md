## 录制环境准备（开录前一次性搞定）

本作品构建对 PATH 较敏感，请固定使用以下配方（Git Bash），避免 `cjpm build` 偶发 exit 127/139：

```bash
export CANGJIE_HOME='D:\CodeWorkspace\compiler-diagnostic\cangjie-sdk-1.1.3\cangjie'
export PATH="$CANGJIE_HOME/bin:$CANGJIE_HOME/tools/bin:$CANGJIE_HOME/tools/lib:$CANGJIE_HOME/runtime/lib/windows_x86_64_cjnative:$PATH"
export CJC_JOBS=1
# 跨 SDK / 增量损坏时务必先清： rm -rf target && cjpm build --jobs 1
```

录制前先跑一遍 `rm -rf target && cjpm build --jobs 1` 确认 `cjpm build success`，并把终端字体放大。

## 分镜 1 · 开场（0:00–0:25）

- **画面**：标题页「编译器诊断质量提升 compiler-diagnostic ｜ 仓颉挑战赛 K1」，下方副标题“结构化诊断 · LSP 兼容 JSON · 性能零劣化 · 1519 稳定错误码”。
- **解说**：大家好，这是仓颉编译器诊断质量提升作品。它让仓颉编译器的报错从“一段话”变成“结构化数据”，可被 IDE、AI 助手直接消费，显著提升排错效率。

## 分镜 2 · 痛点与能力（0:25–0:55）

- **画面**：左右对比。左：传统报错文本（无结构、无修复建议）；右：本作品输出 JSON（`code`/`severity`/`span`/`fix`/`rootCause`/`candidates`）。下方数字浮层「1519 错误码 · 40 类 · 零孤儿」。
- **解说**：传统诊断缺少统一结构与修复建议。本作品提供 **1519 个稳定错误码（E00–E90 共 40 类）**、结构化字段、修复建议（`fix`）、候选符号（`candidates` 含类型，如 `var1(variable)`），以及结构化根因字段（`rootCause`），并输出符合 LSP 规范的 JSON。

## 分镜 3 · 构建与三种运行模式（0:55–2:00）

- **画面**：终端依次执行：
  1. `cjpm build` → 显示 exit 0、零警告。
  2. `cjpm run` → 文本输出示例（含 `候选符号: var1(variable), var2(variable)` 与末尾性能基线 `性能基准: ... memRatio=1.033x (通过)`）。
  3. `cjpm run -- --diagnostic=json` → JSON 输出，高亮 `rootCause`（如 `"类型转换失败"`）与 `candidates`（结构化 `[{"name":"var1","kind":"variable"}]`）。
  4. `cjpm run -- --diagnostic=lsp` → LSP 模式，高亮 `range.character`（非 `column`）、数字 `severity`（1=Error）、`codeAction`（一键修复 quickfix，含 `edit.changes`）。
- **解说**：构建零警告通过。运行支持文本、JSON、LSP 三种模式：JSON 模式补齐结构化 `rootCause` 与带类型的 `candidates`，便于 AI 助手归因；LSP 模式直接输出 `Diagnostic[]`，字段严格对齐 Language Server Protocol，可被 VS Code / 各类 IDE 原生消费，`codeAction` 直接映射为一键修复。

## 分镜 4 · 三层测试（2:00–2:40）

- **画面**：终端执行 `cjpm test`，展示 `Summary: TOTAL: 80 / PASSED: 80 / FAILED: 0`（ut 46 · hlt 22 · llt 12）；再执行 `python ci_test/ciTest.py hlt` 与 `... llt` 展示集成/低级测试全绿。
- **解说**：测试覆盖单元（UT）、集成（HLT）、低级（LLT）三层，共 80 个用例全部通过，验证错误码体系与输出格式的稳定性。

## 分镜 5 · 静态检查与规范（2:40–3:15）

- **画面**：终端执行 `cjlint -f src -o cjlint_report.json`，展示报告汇总 `MANDATORY = 0`；注释说明 482 条均为 `SUGGESTIONS`（非阻断）。
- **解说**：通过 cjlint 静态检查，无 error 级（MANDATORY）违规；剩余提示均为风格建议，不阻断赛事门禁。

## 分镜 6 · 收尾与价值（3:15–3:50）

- **画面**：回到标题页，列出四项核心亮点（结构化诊断 + 根因归因 / LSP 兼容 JSON / 真实性能基线零劣化 / 1519 稳定错误码），附双仓库地址。
- **解说**：本作品无外部依赖、纯仓颉实现，已具备提交条件，可立即用于 IDE 集成与 AI 辅助开发，并为仓颉生态贡献了「软件工程专家团」。

## 录制要点

- 终端字体放大，确保命令与输出清晰可读。
- 关键输出（exit 0、TOTAL 80 PASSED 80、MANDATORY = 0、JSON 的 rootCause/candidates、LSP 的 range/severity/codeAction）可适当定格或加高亮。
- 画外音避免念代码，讲“做了什么、为什么有用”。
- LSP 与 JSON 两模式是核心创新点，建议各给 3–5 秒特写，对照高亮字段。
- 结尾保留 2 秒静帧，便于裁剪。
