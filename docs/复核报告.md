## 二、构建门禁实测结果（最关键证据）

用官方 **1.1.3** 工具链执行 `cjpm build`：**构建失败（exit ≠ 0）**。

- 初次（仅补全 `import std.collection.*` 后）仍有 **11 处错误**，归 4 类：
  1. `invalid named arguments prefix 'code:'` — `ParserDiagnostic.cj:7,17,26,35,44`、`SemaDiagnostic.cj:8,15,23,31`（共 7 处）：`DiagnosticBuilder(code:, message:, span:)` 命名实参在 1.1.3 不被接受。
  2. `generics type arguments do not match the constraint of 'Class-HashMap<...>'` — `DiagnosticCollector.cj:36`：`groupByCode()` 用 `HashMap<ErrorCode, ...>()`，枚举 `ErrorCode` 不满足 HashMap key 约束。
  3. `expected expression after '..', found '<'` — `PerfBenchmark.cj:42`：`0..<100` 区间语法不被接受。
  4. `expected '{', found 'current'` — `PerfBenchmark.cj:66-67`：`if (cond) e else e` 无大括号表达式不被接受。
- **结论**：正式源码在声明的 1.1.3 工具链下**根本无法编译**。因此：
  - 历史 `docs/19-性能基准测试报告.md`（"构建成功/性能 1.00x"）、`docs/20-覆盖率报告.md`（"97% 覆盖率"）均属**无效结论**；`docs/20` 自身也已承认覆盖率数据基于无法编译的代码。
  - 验收门禁"构建 exit 0 + warning=0"、"cjlint 无 warning"、"ciTest llt/hlt 全绿"**当前全部不可达成**（代码不编译，测试无法运行）。

## 四、逐条问题与证据

### 4.1 最致命：项目无法编译（阻断级）
- 见第二节。根因 = 源码按"想象的 1.1.3 API"编写，实际与真实 1.1.3 在**命名实参、集合导入、区间语法、if 表达式、HashMap key 约束**上均不兼容。
- 影响：所有依赖编译的门禁（构建/warning/cjlint/测试/性能）**全部失效**。

### 4.2 交付①/② 的范围错位（重要级）
- 仓库实现的是**诊断数据模型 + 输出层（库/演示）**，而非对编译器 Parser/Sema **前端的真实集成**。
- `src/main.cj:27-59` 用手写方式调用 `reportXxx(...)` 生成"示例诊断"，**没有任何词法/语法/类型分析从真实源码产生诊断**。即"诊断优化"目前只是消息模板，未接入编译器。
- 位置"准确"在真实场景无法成立：`main.cj:28-45` 中 9 条诊断共用同一 `span1 = line10:col5-20`。

### 4.3 交付③ JSON 字段的 IDE/AI 适配偏差（重要级）
- `src/output/JSONOutput.cj` 输出 `{"diagnostics":[...]}`；LSP 规范是**直接返回 `Diagnostic[]` 数组**，且位置字段名为 `range`（非 `span`）。当前结构需 IDE/AI 侧做适配转换。
- `JSONSchema.cj:18` `severity` enum 仅 `["error","warning"]`，但 `DiagnosticMessage.severity` 是自由字符串（代码仅用 `"error"`），若未来出现 `"info"` 会与 schema 不符。
- `FixSuggestion`(`Diagnostics.cj:70-93`) 含 `replacement` 但多数调用未设目标 `span`（`ParserDiagnostic.cj:12` 仅 description+replacement），且未映射为 LSP `CodeAction`/`WorkspaceEdit`，故"可执行修复"在 IDE 中不可直接应用。

### 4.4 交付④ 缺失项（重要级）
- **贡献指南缺失**：全仓无 `CONTRIBUTING.md`/贡献规范文档（grep 仅挑战赛相关文档提及"贡献"），不满足交付④。
- **样例库覆盖不全**：`examples/error_samples/` 仅 5 个 Parser 样例（unterminated_string / type_mismatch / undefined_ident / bracket_mismatch / expr_syntax_error），**无 E1001-E1004 任何 Sema 样例**。
- **回归基线不可用**：`ci_test.cfg` 硬编码 `3rd_party_root = /home/lyq/workspace`、`home = /home/lyq/cangjie_env`（个人 Linux 路径，Windows 本机不可复现）；`compile_options = --test -Woff all --dy-std` 关掉所有 warning，使"warning=0"门禁形同虚设；且无"黄金输出(golden)"基线定义，仅断言式测试。

### 4.5 指标 B/D 的结构性缺陷（重要级）
- `DiagnosticMessage`(`Diagnostics.cj:137-205`) 字段为 `code/severity/message/span/fix/related/candidates`——**无独立 `rootCause` 字段、无 `candidateTypes` 字段**。复杂语义错误的"根因"被拼进 message 文本，"候选类型"能力缺失。
- `PerfBenchmark.cj` 的基线对比逻辑（`compareWithBaseline`）从未被调用，`estimateMemoryUsage`(`PerfBenchmark.cj:47-56`) 用 `256B*条数` 估算，非真实测量 → 指标 D 当前**不可证**。

## 五、整改优先级清单

### 阻断级（必须先解决，否则一切免谈）
1. **让项目在 1.1.3 真实编译**：
   - 为所有 `.cj` 补 `import std.collection.*`（List/Map/ArrayList/HashMap）与必要的 `import std.convert.*`（StringBuilder）；
   - 将 `DiagnosticBuilder(code:, message:, span:)` 命名实参改为**位置实参**（`ParserDiagnostic.cj` / `SemaDiagnostic.cj` 全部调用点）；
   - `DiagnosticCollector.cj:36` 的 `HashMap<ErrorCode,...>` 改为满足约束的 key 类型（或让 `ErrorCode` 满足 `Hashable`/`Equatable`，或换用 `Map` 的合规实现）；
   - `PerfBenchmark.cj:42` `0..<100` → 兼容写法（如 `for (i in 0..100)` 或 `Range` 构造）；
   - `PerfBenchmark.cj:66-67` 的 `if (cond) e else e` 补 `{}` 大括号。

### 重要级
2. 把诊断**接入真实前端**：提供最小 Parser/Sema 桩，使诊断从真实源码（而非 `main.cj` 硬编码）产生，位置来自真实 `SourceLoc`。
3. `DiagnosticMessage` 增加结构化 `rootCause: Option<String>` 与 `candidateTypes: Option<List<String>>` 字段，并在 JSON 中输出。
4. JSON 输出对齐 LSP：`range` 替代 `span`、`Diagnostic[]` 直接出（或提供 LSP 兼容模式）、`severity` enum 补 `"info"`。
5. `FixSuggestion` 始终携带目标 `span`，并映射为 LSP `CodeAction`（可执行修复）。
6. 补齐交付④：新增 `CONTRIBUTING.md`；`examples/error_samples/` 增加 E1001-E1004 Sema 样例；`ci_test.cfg` 去除个人路径与 `-Woff all`，改为可复现配置并定义 golden 基线。

### 建议级
7. 真实性能基线：在 `main` 中实际调用 `compareWithBaseline` 并以真实测量值（非估算公式）判定 ≤1.05x。
8. `cjpm.toml` 的 `cjc-version` 与实际工具链保持一致；文档中版本表述统一。

## 六、总体结论

**项目当前不满足"4 交付 + 4 指标"中的任何一项"完整达成"。**

- 架构上存在**范围错位**：实现的是"诊断表示与输出层"，而非对编译器 Parser/Sema 前端的真实诊断优化；"高频语法错误/类型/泛型/重载/可见性诊断优化"目前仅为消息模板与手写样例。
- **最致命硬伤**：在用户指定的官方 1.1.3 工具链下**无法编译**（11 处真实错误），导致构建/warning/cjlint/测试/性能全部门禁失效，历史"构建成功/97% 覆盖率"结论作废。
- 数据模型设计（ErrorCode 枚举稳定、related/candidates/fix 扩展字段）方向正确，是后续修复的良好基础；但需在"真实前端接入、结构化根因/候选类型、LSP 兼容、可执行修复、回归基线与贡献指南"五处补齐，方能达到用户给出的交付与验收口径。
