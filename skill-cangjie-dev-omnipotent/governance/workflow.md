# 治理引擎主工作流（法庭式评审）

> 整合自 code_quality_governance_swarm/workflow.md 与 sub_skills/*_trial。
> 每个交付阶段完成后由主理人触发本工作流作为质量门禁。

## 触发
交付专家产出阶段交付物后自动触发；或用户直接说「评审这段仓颉代码 / 审一下这个方案」进入纯治理模式。

## 门禁子流程（七阶段庭审）

```
1 前置准备  意图澄清官补全上下文 + 环境摸底(cj --version/cjpm check) + 特征预扫描
2 分级路由  路由法官六维打分 → 匹配 L0-L4 档位 → 成本预估
3 侦查指控  控方律师输出疑点清单 → 仓颉工具硬校验(cj build/cj test/cjlint)交叉验证 → 一级监察质检
4 控辩对抗  辩方逐条辩护(附证据) ↔ 控方交叉质证 → 一级监察质检
5 法官判决  主审法官按 governance-core.md 出具判决书 → 一级监察质检
6 两级监察  总监察长六维度独立复核 → 集体幻觉触发二次复核
7 动态升降档 依缺陷数量自动升降档；判决分流
```

## 判决分流

- 通过且无 P0/P1 → 阶段 PASSED → 人在闭环确认 → 自动推进下一阶段
- 需整改 → 执行官逐条落实 P0/P1（用 cj build/cj test 验证）→ 审判庭重组（全新实例，从上一步重新开始，轮次上下文仅参考）→ 回到阶段 3
- 通过但有 P2 → 阶段 PASSED，P2 记录待后续
- 轮次超限 → 升级处理策略 A/B/C/D

## 四种运行模式

| 模式 | 说明 |
|------|------|
| 全生命周期 | 需求→架构→编码→测试→部署，每阶段多轮循环直至通过（默认） |
| 单阶段交付 | 仅执行指定阶段 |
| 纯治理 | 仅对已有交付物评审（不交付） |
| 紧急修复 | 跳过部分门禁直接修复，标注并事后补审（人在闭环强制确认） |

## 并行与错误恢复

- 并行：控辩并行准备、多工具硬校验并行(cjlint+cjsc)、独立整改项并行
- 检查点：每阶段完成保存 checkpoint.json，支持断点续跑
- 降级：仓颉工具不可用时降级为纯模型评审，标注「无工具支撑」
- 成本熔断：累计 token 超阈值触发负向终止

## 收尾钩子

后置沉淀 → 自学习闭环（见 human-and-learning-rules.md）→ 卷宗归档 → 成本报告 → 交付物追溯链。
